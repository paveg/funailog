## はじめに

2026-11-01 の未明、自宅の回線で IPv4 だけが約 7.5 時間止まりました。IPv6 は生きていたので、気づいたのは朝になってからです。それも通知ではなく、「なんだか回線が死んでいる気がする」という体感でした。

あとで調べると、自宅の監視（Prometheus と Alertmanager）は障害の開始から 5 分で正しく検知していました。それなのに、Discord には 1 件も通知が届いていません。原因は 2 つ重なっていました。

- 不通のあいだは、通知そのものがインターネット経由なので送れない
- 復旧したあとも、Alertmanager の通知を Discord が HTTP 400 で拒否していた。こちらは障害と関係がなく、3 か月前に入れた設定の誤りがずっと潜んでいた

この記事では、2 つ目の原因を Alertmanager のソースまで追った経緯と、その修正、そして修正しても残る穴を書きます。回線が止まった原因（ゲートウェイの自動更新）は、メーカーのサポートの回答を待っているので、別の記事で書く予定です。

なお、この記事は調査・事実確認に AI（Claude）を使い、AI が書いた下書きを僕が校正する形で執筆しています。

### 想定読者

- Prometheus と Alertmanager で、自宅や小さなチームのシステムを監視している人
- Alertmanager の `discord_configs` で、Discord に通知を飛ばしている人。特に、embed を使わずに本文だけで送ろうとしている人
- 「監視は動いているはずなのに、通知が来ない」という状況を一度でも疑ったことがある人

Prometheus のルールの書き方や、Alertmanager の基本は説明しません。

## 監視の構成

自宅の Proxmox 上に監視用の LXC を 1 台置き、Prometheus、blackbox_exporter、Alertmanager を動かしています。回線の死活は、blackbox_exporter の 2 種類のプローブで見ています。

- ICMP: `1.1.1.1` と `8.8.8.8`、それにゲートウェイ（192.168.10.1）への ping
- HTTPS: 外部の公開サイトへのリクエスト

回線が死んだと判断するアラート `WanDown` は、この 2 種類を組み合わせています。

```yaml
- alert: WanDown
  expr: |
    max(probe_success{job="blackbox-icmp", instance=~"1\\.1\\.1\\.1|8\\.8\\.8\\.8"}) == 0
      and on()
    max(probe_success{job="blackbox-https-public"}) == 0
      and on()
    max(probe_success{job="blackbox-icmp", instance="192.168.10.1"}) == 1
  for: 5m
  labels:
    severity: critical
```

外への ICMP も HTTPS も全滅していて、ゲートウェイだけは応答する。この状態が 5 分続いたら発火します。ゲートウェイまで応答しないなら、それは回線ではなく家の中の問題なので、別のアラートに任せています。

ICMP と HTTPS の 2 本立てにしたのは、2026-08-01 に ICMP のプローバーだけが壊れ、このアラートが 13 時間誤報し続けたからです。1 種類のプローブだけでは、「回線が死んだ」のか「測る側が死んだ」のかを区別できません。

プローブは、すべて IPv4 に固定しています（`preferred_ip_protocol: ip4`）。HTTPS の宛先は `https://1.1.1.1/cdn-cgi/trace` と `https://dns.google/resolve?name=example.com` の 2 つで、後者は IPv6 でも引けるホスト名です。今回の障害は IPv6 が生きていて IPv4 だけが止まる形だったので、固定していなければ `dns.google` へのプローブが IPv6 で成功し、`WanDown` の条件が崩れていた可能性があります（監視用の LXC から IPv6 で外に出られたかは確かめていません）。回線は v6 プラス（MAP-E）で、IPv4 は IPv6 のトンネルの上を通っています。その構成は [ISP を乗り換えた記事](/blog/2026/isp-migration-nuro-to-enhikari) に書きました。

## 検知は正しかった

Prometheus の `ALERTS` を見ると、`WanDown` は 04:29 に発火し、11:54 に解消していました。ゲートウェイの自動更新が 04:24〜04:29 に走り、11:53 に僕が手で直すまで、という障害の区間とほぼ一致します。

06:00 時点の 3 つの条件の値は、外への ICMP が `0`、HTTPS が `0`、ゲートウェイへの ICMP が `1` です。ルールが想定していたとおりの形でした。

監視は、正しい時刻に、正しい理由で鳴っていました。問題はその先にあります。

## 不通のあいだに届かないのは当然

Alertmanager のログには、04:34 から 5 分おきに次の行が並んでいました。

```text
Notify for alerts failed ... WanDown ... context deadline exceeded
```

Discord への送信がタイムアウトしています。IPv4 が止まっているのだから、これは当然です。

ただ、IPv6 は生きていました。それなら IPv6 で Discord に届かないのか、と考えて DNS を引いてみると、`discord.com` には AAAA レコードがありません。

```bash
$ dig +short discord.com AAAA
$ dig +short discord.com A
162.159.x.x
...
```

Discord には IPv4 でしか届かないので、IPv4 が止まった時点で通知の経路は切れていました。

## 復旧したあとも届かない

おかしいのは、11:53 に IPv4 が戻ったあとです。復旧すれば、溜まっていた通知や解消の通知が届くはずでした。ところが、ログにはタイムアウトの代わりに別のエラーが出ていました。

```text
unexpected status code 400: {"embeds": ["0"]}
```

Discord が、Alertmanager の送ったリクエストを 400 で拒否しています。`{"embeds": ["0"]}` は、「0 番目の embed が不正」と読めます。

Alertmanager の送信カウンターを見ると、状況はもっと悪いことが分かりました。コンテナを起動した 10-27 以降の数字です。

| 指標（`integration="discord"`）           |  値 |
| :---------------------------------------- | --: |
| `alertmanager_notifications_total`        | 117 |
| `alertmanager_notifications_failed_total` | 117 |
| うち `reason="contextDeadlineExceeded"`   | 108 |
| うち `reason="other"`（400）              |   9 |

**117 回送って、117 回とも失敗していました。成功は 0 回です。** 最初の 400 は 11:54 なので、それより前の失敗はすべてタイムアウトで、108 回はどれも障害中のものです。5 分おきの `WanDown` だけなら 90 回ほどなので、障害中に送ろうとしたほかのアラートの分も含まれていると考えられます（内訳は確かめていません）。一方、400 の 9 回はどれも復旧後のもので、回線と関係がありません。回線が正常でも、Discord への通知は届かない状態だったことになります。

この間、Discord に届いたのは、Home Assistant の ping の監視が Alertmanager とは別の経路で送っている通知だけでした。11:56 に「Recovered: WAN (1.1.1.1)」が 1 件届いています。障害が始まったことを知らせる通知は、どの経路からも届いていません。

いつから届かなかったのかは分かりません。設定を変えたのは 2026-08-02 なので、そこからずっと届いていなかった可能性があります。ただ、それ以前のカウンターはコンテナの再起動で消えていて、確かめられませんでした。

## 原因は Alertmanager が必ず embed を送ること

2026-08-02 の変更では、Discord の通知を embed を使わずに本文（`content`）だけで送ろうとしていました。Discord のスマホアプリでは embed の中の文字を選択できず、アラートの内容をコピーできないからです。

そのときの設定は次のとおりです。

```yaml
discord_configs:
  - webhook_url_file: /run/secrets/discord_webhook
    send_resolved: true
    title: ''
    message: ''
    content: |-
      {{ if eq .Status "firing" }}🔴 FIRING{{ else }}✅ RESOLVED{{ end }} · {{ .CommonLabels.alertname }}{{ with .CommonLabels.severity }} · {{ . }}{{ end }}
      ...
```

設定のコメントには、「title と message を空にすれば embed が消える」と書いていました。これが誤りでした。

Alertmanager v0.33.1 の Discord 通知の実装[^am-discord]を読むと、送る JSON の構造体は次のようになっています。

```go
type webhookEmbed struct {
    Title       string `json:"title"`
    Description string `json:"description"`
    Color       int    `json:"color"`
}
```

`title` と `description` の JSON タグに `omitempty` がありません。そして送信のたびに、embed を 1 つ、条件なしに組み立てています。

```go
w := webhook{
    Content:  content,
    Username: n.conf.Username,
    Embeds: []webhookEmbed{{
        Title:       title,
        Description: description,
        Color:       color,
    }},
}
```

`color` は、発火中なら赤、解消なら緑、それ以外なら灰色が必ず入ります。つまり title と message を空にしても embed は消えず、**色だけが入った中身の空の embed が送られます。** Discord はこれを 400 `{"embeds": ["0"]}` で拒否していました。

設定を変えたときに、テストのアラートを 1 本流していれば、その場で気づけたはずです。8 月の時点では、`amtool check-config` で文法は確かめていました。ただ、本文だけで届くはずだという思い込みのまま、届くところまでは見ていませんでした。

## 修正して、テストのアラートで確かめる

embed は消せないので、中身を入れて有効な embed にします。title にアラート名を 1 行だけ入れ、コピーしたい本文は `content` に残しました。

```yaml
title: '{{ if eq .Status "firing" }}🔴{{ else }}✅{{ end }} {{ .CommonLabels.alertname }}'
message: ''
```

失敗の合計は、カウンターを見たあとにもう 1 回増え、修正の直前で 118 回になっていました。`amtool check-config` で設定の文法を確かめ、Alertmanager に設定を読み直させました。そのあと、送信の成功回数（`notifications_total` から `failed_total` を引いた値）は次のように増えています。

| 時点                                                         | 成功 | 失敗（合計） |
| :----------------------------------------------------------- | ---: | -----------: |
| 修正の直前                                                   |    0 |          118 |
| 設定の読み直し後（その時点で発火中だった別のアラートを再送） |    1 |          118 |
| テストのアラートを投入した後                                 |    2 |          118 |

テストのアラートは、`DiscordDeliveryTest` という名前で Alertmanager の API に直接入れました。Discord には `🔴 FIRING · DiscordDeliveryTest · info` が、embed のタイトル付きで届いています。

これで分かったのは、title さえあれば、description（`message`）が空でも Discord は受理するということです。message を空にしたこと自体は問題ではありませんでした。

## 修正しても残る穴

400 は直りました。ただ、今回の障害そのものを通知で知る手段は、まだありません。

回線が止まると、家の中から Discord に知らせる仕組みは、どう作っても動きません。今回の 108 回のタイムアウトがそれです。家の中の監視が正しく鳴っても、その声が外に出ていけません。

定石は、外部のハートビートです。healthchecks.io のようなサービスに、監視用の LXC から定期的に生存報告を送り、報告が途絶えたら外部側がメールやプッシュで知らせます。報告が「届かなくなった」ことに外側が気づく仕組みなので、回線が死んでも機能します。これはまだ手を付けていません。

`alertmanager_notifications_failed_total` が増えたら鳴るアラートを足す案も考えました。ただ、そのアラートの通知も同じ Discord の経路を通ります。経路が壊れていれば、壊れたことを知らせる通知も届きません。今回の 400 も、そのアラートの通知が同じ空の embed で拒否されるので、気づく手段にはなりません。回線断にも 400 にも効かないので、外部ハートビートの代わりにはなりません。

なお、Proxmox のバックアップの通知は、毎週の成功通知そのものをハートビートとして扱っています（[Home Assistant を Proxmox に入れた記事](/blog/2026/home-assistant-m920q-proxmox)）。こちらは「来ないこと」に人が気づく前提で、自動で知らせてはくれません。

## まとめ

- 監視は 5 分で正しく検知していた。届かなかったのは通知の経路のほう
- 不通のあいだは、`discord.com` に AAAA レコードが無いため、IPv6 が生きていても届かない
- Alertmanager v0.33.1 の Discord 通知は、title と message を空にしても embed を必ず 1 つ送る。中身の空の embed を Discord は 400 で拒否する
- title を 1 行入れれば、message は空のままでも受理される

いちばんの教訓は、受け取る側が静かでも、送る側が正常とは限らないことです。届いたかどうかは、送った側のカウンター（`alertmanager_notifications_failed_total`）にしか出ていませんでした。通知の設定を変えたら、テストのアラートを 1 本流し、届くところまで見る。次は外部ハートビートを入れて、回線が死んだときにも気づけるようにします。

それでは、またね。
