# funailog の新しい記事を書く

グローバルの `writing` スキル（article モード）を土台に、funailog で必要な工程を足した手順です。工程は順番どおりに実行します。短い記事でも、急ぎでも同じです。

## 適用範囲

| 条件                               | 扱い                                                                                                    |
| :--------------------------------- | :------------------------------------------------------------------------------------------------------ |
| 対象の mdx がすでに存在する        | このスキルの対象外。追記は `.claude/rules/blog-writing-style.md` の「追記」、校正は `writing-proofread` |
| 製品レビュー、比較、おすすめの記事 | 工程 2 と 4 で `seo-affiliate-article` の型を併用する。工程はこのスキルに従う                           |
| frontmatter に `series` がある     | 同じシリーズの既存の記事を工程 4 のお手本にし、シリーズの規約（slug、末尾のリンク）をそろえる           |

## 工程

|   # | 工程                     | 使うもの                                | 筆者への確認                    |
| --: | :----------------------- | :-------------------------------------- | :------------------------------ |
|   1 | 企画と素材を集める       | `writing` の Phase 0〜2                 | Phase 1 で確認する              |
|   2 | 構成案を作る             | `writing` の Phase 3                    | 承認を取る                      |
|   3 | grill                    | この文書                                | 質問する                        |
|   4 | ドラフトを書く           | `writing` の Phase 4                    | なし                            |
|   5 | 図を描く                 | `excalidraw-diagram`                    | なし                            |
|   6 | 主張と公開可否を確かめる | `verify-doc-claims`、`fact-check.md` §5 | 未確認の行の扱いを聞く          |
|   7 | 校正する                 | `writing-proofread`                     | なし                            |
|   8 | SEO を監査する           | `seo-auditor`                           | title を大きく変えるときだけ    |
|   9 | 敵対的レビューを通す     | `adversarial-review`、`skeptic`         | 3 回直しても残った行を提示する  |
|  10 | 公開の PR を出す         | この文書                                | push の前に最終稿を読んでもらう |

## 1. 企画と素材

素材に実測待ちの事実があれば、待つ、推論として書く、その話を落とす、のどれにするかを Phase 1 で筆者に選んでもらいます。写真やスクリーンショットは、ここで受け取ります。

## 2. 構成案に必ず入れる列

セクションごとの表に「図」の列を置き、次のどちらかを書きます。

- その図が答える問い（例: 「どこで同じ回線に合流するか」）
- `なし`

全セクションが `なし` なら、理由を 1 行書きます。構成案の承認が工程 5 を省く承認になります。Excalidraw に向くのは、層、境界、入れ子、物理的な配置、時系列のように、位置や囲みに意味がある図です。シーケンス図、一直線の流れ、ツリーは mermaid やテキストにします。

## 3. grill

構成案の承認後、下書きの前に実行します。素材がそろっていても実行します。

`~/.claude/skills/grill-me/SKILL.md` の Phase 1（Interview）を読み、その聞き方に従います。1 ラウンドに、答えが互いに依存しない質問をまとめ、番号と推奨の答えを付けて聞きます。素材やリポジトリで分かることは聞きません。筆者しか知らない事実で推奨を出せない質問は、素材から読める仮説を付けます。

洗い出す対象は次のとおりです。

- 素材にない、筆者しか知らない事実（なぜそうしたか、何に困ったか）
- 構成案で最も弱い主張と、その反例
- 素材の中の推論（実測していないのに言い切れそうな箇所）
- 記事に入れてよいか迷うもの（未修正の弱点、監視していない経路、外から届くサービスの構成、個人を特定できる情報、写真ごとの公開可否）
- 読者に持ち帰ってほしいこと

`grill-me` の Phase 2（設計文書や ADR を書く）は行いません。答えは素材ノートに「筆者談」と書いて足し、公開しないと決めたものは「公開しない」リストに書きます。構成案も更新します。聞くことが無くなるか、筆者が「もう十分」と言ったら終わります。

## 4. ドラフト

- `origin/main` から記事用のブランチを切ります
- `isPublished: false` のまま書きます
- 導入の末尾に、AI を使った範囲を書きます（例: 「調査・事実確認に AI（Claude）を使い、AI が書いた下書きを僕が校正する形で執筆しています」）。実際に担った作業に合わせ、工程 10 で筆者に確かめます
- 読者が判断に使わない細かい数値は丸めます。根拠になる数値は残します
- 自然な日本語で言い切れるカタカナ語は置き換えます。API の項目名や定着した語は残します
- 金額は円で書きます。別の概念を同じ語でまとめません。筆者が未経験の領域は、そう明記します
- 素材ノートと grill の答えは、記事の材料です。「公開しない」リストのものは書きません
- 確認待ちの箇所は `{/* 要確認: ... */}` と書きます（MDX では `<!-- -->` が構文エラーになります）。公開前にすべて解消します

**写真とスクリーンショット**: 撮影日時など根拠に使う情報を素材ノートに写してから、次のコマンドでリポジトリに入れます。EXIF が消えるので、順番を逆にしません。

```bash
# HEIC のときは先に JPEG にする（magick では開けません）
sips -s format jpeg in.heic --out in.jpg
magick in.jpg -auto-orient -profile "/System/Library/ColorSync/Profiles/sRGB Profile.icc" -resize '2400x2400>' -strip src/assets/blog/{year}/{slug}-{n}.jpg
```

## 5. 図

図の要素を、色や線種の凡例も含めて 1 行 1 主張に分け、描く前に一次資料で裏を取って `.ai/{slug}-diagrams.md` に書きます。本文に無い事実は、図だけに描かず本文にも足します。

画風は `excalidraw-diagram` の既定（`roughness: 0`、`fontFamily: 3`）ではなく、既存の図に合わせます（`roughness: 1`、`fontFamily: 5`）。

```bash
# 元ファイルは .ai/diagrams/{name}.excalidraw に置く
(cd ~/.claude/skills/excalidraw-diagram/references && uv run python render_excalidraw.py "{repo の絶対パス}/.ai/diagrams/{name}.excalidraw")
# 横 2400px に縮小し、メタデータを消して書き出す
magick .ai/diagrams/{name}.png -resize '2400x>' -strip src/assets/blog/{year}/{slug}-{name}.png
```

レンダリングした PNG を開いて、`.ai/{slug}-diagrams.md` の行と 1 つずつ照合します。埋め込みは `@/components/markdown/Image.astro` で `width={1200}` を指定します。`height` は省略できます（Astro が縦横比から求めます）。

## 6. 主張と公開可否

**主張**: パスを明示して `verify-doc-claims` を実行します。既定の `*.md` では `.mdx` も `.ai/` も対象になりません。

```text
verify-doc-claims src/content/blog/{year}/{slug}.mdx .ai/{slug}-diagrams.md
```

工程 5 を省いた記事では、図の仕様のパスを渡しません。

本文、図、alt、title、description、掲載したコードが対象です。本文の全リンクを開き、文を支えているかも確かめます。筆者談の扱いは次の表に従います。`fact-check.md` の「ユーザー談は未検証」より、この表を優先します。感想は検証の対象にしません。経験談に仕様、測った数値、払った金額が含まれるときは、その部分だけ 2 行目に従います。日付や期間は経緯として 1 行目に従います。「体感で 2 倍」のように測っていないと分かる書き方は、感想として扱います。

| 主張の種類                                             | 扱い                                                       |
| :----------------------------------------------------- | :--------------------------------------------------------- |
| 筆者の経験、経緯                                       | 筆者が一次資料なので、素材ノートの筆者談と一致すれば確認済 |
| 仕様、製品や他者についての事実、測った数値、払った金額 | 一次資料（公式ページ、ログ、領収書）が付くまで未確認       |

未確認の行は、行ごとに、確かめる、推論や筆者の記憶として書く、削る、のどれかを筆者に選んでもらいます。

**公開可否**: 記事の分類に関わらず、次をすべて行います。

- `fact-check.md` §5 の開示チェックを、本文、frontmatter、図の中の文字に対して行う。地名は、自宅や勤務先など筆者の居場所につながるものを伏せ、旅先の地名は残す
- 「公開しない」リストとドラフトを照合する
- `pnpm lint:content` を実行する（伏せる情報で拾うのは、本名、MAC アドレス、グローバル IPv6、メールアドレスだけです）
- 載せる画像を 1 枚ずつ開く。frontmatter の `heroImage`、`public/` の画像、外部 URL の画像も含む。画像の中の ID やホスト名、顔、車のナンバー、部屋番号、映り込み、撮影禁止の場所を見て、画面の数値が本文と一致するかも確かめる
- `identify -verbose {画像} | grep -E 'exif:(Make|Model|GPS|DateTime)'` で、リポジトリに入れる画像に撮影情報が無いことを確かめる（出力が無ければ合格）。`public/` の画像と、`astro.config.ts` の `image.domains` に無いドメインの画像は、ビルドで変換されずそのまま配信されます

## 7. 校正

記事のパスと、文体の規約（`.claude/rules/blog-writing-style.md` と選んだ文体プロファイル）を名指しして、`writing-proofread` を fix モードで実行します。

## 8. SEO

`seo-auditor` に、記事のパス、GSC の CSV のパス、集計期間を渡します。新しい記事は、ヘッダーだけの CSV を `.ai/gsc-{slug}.csv` に作って渡します。列は `query,clicks,impressions,ctr,position` です。出力の冒頭が「検索データ不足」になるのが正常です。主題や狙う語が変わる title の提案が出たら、筆者に確認します。

## 9. 敵対的レビュー

`adversarial-review` を、記事のパスと、載せる画像のパス、図があれば図の仕様のパスを渡して実行します。記事の主張は `doc` に分類せず、次の観点ごとに 1 体ずつ `skeptic` に記事全体を渡します（下書きを書いたセッションが自分で判定しないためです）。証拠の段階（記事の主張は `walked`、コマンドで試せる確認は `ran`）も伝えます。観点が当てはまらない記事（コードが無いときの読者への害など）は、理由を書いて飛ばします。

反証させる観点は次のとおりです。

- title、description、見出し、本文、alt、図のあいだの矛盾
- 言い過ぎ（反例が 1 つでもある断定、今の設定の話を一般論にしたもの）
- 図の凡例と、実際の色や線の食い違い
- 読者への害（`curl | sh`、TLS 検証の無効化、広すぎる権限、鍵の直書き、`rm -rf`。採用しない案として書くならそう明記されているか。店や他者についての断定も含む）
- 攻撃の手がかり（この記事だけで、外から何ができるようになるか。筆者や同行者を特定できるか）

`skeptic` は 1 回に 1 つの判定を返すので、REFUTED を直したら、直した本文でその観点の `skeptic` をもう一度実行します。観点ごとに CONFIRMED か、理由つきの UNVERIFIABLE になれば PASS です。`evidence stopped at ...`（一次資料に届かなかった）は PASS の理由にしません。

同じ文が 3 回直しても REFUTED か証拠不足のままなら、その文を未検証と明記するか削り、筆者に提示します。別の文の REFUTED は数え直します。筆者が答えるまでは FAIL のままです。筆者が残すと決めた文は、完成レポートに書いて対象から外し、その観点を再実行します。

## 10. 公開

工程 9 が PASS になってから進めます。

1. `isPublished: true` にする
2. 関連する既存の記事があれば、そこからこの記事へリンクを 1 本張る（公開記事から下書きへのリンクは検査で落ちるので、ここで張ります）。足した文は `skeptic` で本文と照合する。関連する記事が無ければ、その旨を完成レポートに書く
3. 新しい外部 URL を単独行に置いたなら `pnpm link-cards:warm` を実行し、`src/data/link-cards.json` の更新もコミットに含める
4. `pnpm lint` と `pnpm build` を実行する
5. ローカルにコミットする。push はまだしません
6. 実行した工程と結果を完成レポートにまとめ、`writing` の Phase 7 の項目（最終稿を含む）とあわせて報告する。リポジトリは公開なので、push した内容は履歴に残ります。依頼に PR が含まれていても、筆者が最終稿を読むまで push しません
7. 筆者の返答のあとで push して PR を作り、auto-merge を有効にする。素材ノートや grill の答えを PR 本文やコミットメッセージに写しません

`writing` の Phase 7 は「PR は頼まれたときだけ」と書いていますが、このリポジトリではこの順に従います。

## 省略してよい理由にならないもの

| 出てくる考え                                                    | 実際                                                                                      |
| :-------------------------------------------------------------- | :---------------------------------------------------------------------------------------- |
| 素材はそろっているので grill は要らない                         | grill が集めるのは素材に無い事実です                                                      |
| ファクトチェックと重複するので `verify-doc-claims` は回さない   | 工程 6 がそのファクトチェックです。別の形に置き換えません                                 |
| `verify-doc-claims` を通したので開示チェックは要らない          | 「正しいか」と「公開してよいか」は別の問いです                                            |
| `lint:content` が通ったので公開してよい                         | 公開 IP、ホスト名、鍵、画像の中身は拾いません                                             |
| 短い記事なので反証は 1 点に絞る                                 | 主張が少なければ行が減るだけで、手順は同じです                                            |
| スクリーンショットがあるので図は要らない                        | 図が要らないなら、工程 2 で `なし` と理由を書いて承認を取ります                           |
| PR まで頼まれているので、最終稿は読んでもらわずに push してよい | リポジトリは公開なので、push は公開と同じです。読むのを省くなら、名指しで指示をもらいます |
| 急ぎなので後で直す                                              | 公開した情報は、画像の配信元や履歴に残ります。公開前に通します                            |

工程を減らせるのは、筆者がその工程を名指しして省くと言ったときと、工程 2 の承認で工程 5 を省くときだけです。「急いで」は省く指示ではありません。
