# funailog の記事を書く

グローバルの `writing` スキル（article モード）を土台に、funailog で必要な工程を足した手順です。工程は順番どおりに、すべて実行します。短い記事でも、急ぎでも同じです。

## 工程

|   # | 工程                 | 使うもの                          | 筆者への確認                 |
| --: | :------------------- | :-------------------------------- | :--------------------------- |
|   1 | 企画と素材を集める   | `writing` の Phase 0〜2           | Phase 1 で確認する           |
|   2 | 構成案を作る         | `writing` の Phase 3              | 承認を取る                   |
|   3 | grill                | この文書                          | 質問する                     |
|   4 | ドラフトを書く       | `writing` の Phase 4              | なし                         |
|   5 | 図を描く             | `excalidraw-diagram`              | なし                         |
|   6 | 主張を裏取りする     | `verify-doc-claims`               | 残った未確認の行を聞く       |
|   7 | 校正する             | `writing-proofread` の fix モード | なし                         |
|   8 | SEO を監査する       | `seo-auditor`                     | title を大きく変えるときだけ |
|   9 | 敵対的レビューを通す | `adversarial-review`              | なし                         |
|  10 | 公開の PR を出す     | この文書                          | 完成レポート                 |

## 2. 構成案に必ず入れる列

節ごとの表に「図」の列を置き、次のどちらかを書きます。

- その図が答える問い（例: 「どこで同じ回線に合流するか」）
- `なし`

全節が `なし` なら、理由を構成案に書いて筆者の承認を取ります。Excalidraw に向くのは、層、境界、入れ子、物理的な配置、時系列のように、位置や囲みに意味がある図です。シーケンス図、一直線の流れ、ツリーは mermaid やテキストにします。

## 3. grill

構成案の承認後、下書きの前に、筆者に 1 問ずつ質問します。素材がそろっていても実行します。次の 4 つを、この順に聞きます。

1. 素材にない、筆者しか知らない事実（なぜそうしたか、何に困ったか）
2. 構成案で最も弱い主張と、その反例
3. 素材の中の推論（実測していないのに言い切れそうな箇所）
4. 公開したくないもの、読者に持ち帰ってほしいもの

答えは素材ノートに「筆者談」と書いて足し、構成案を更新します。筆者が「もう十分」と言ったら終わります。

## 4. ドラフト

- `origin/main` から記事用のブランチを切ります
- `isPublished: false` のまま書きます
- 読者が判断に使わない細かい数値は丸めます。根拠になる数値は残します
- 自然な日本語で言い切れるカタカナ語は置き換えます。API の項目名や定着した語は残します

## 5. 図

図の要素を 1 行 1 主張に分けて、描く前に一次資料で裏を取り、`.ai/{slug}-diagrams.md` に書きます。本文に無い事実は、図だけに描かず本文にも足します。画風は既存の図に合わせます（`roughness: 1`、`fontFamily: 5`、`hachure`）。

```bash
# 元ファイルは .ai/diagrams/ に置く。レンダリング後に横 2400px で書き出す
sips -Z 2400 .ai/diagrams/{name}.png --out src/assets/blog/{year}/{name}.png
```

`@/components/markdown/Image.astro` で、`width={1200}` と、実際の縦横比から求めた `height` を指定します。

## 6. 裏取り

本文、図、alt、title、description を対象に `verify-doc-claims` を実行します。`writing` の Phase 5 のファクトチェックは、この工程で行います。あわせて次を確かめます。

- `pnpm lint:content`（内部リンクと、伏せる情報の文字列）
- 記事に載せる画像を 1 枚ずつ開く。文字列の検査では、画像の中の project ID やホスト名を拾えません

## 9. 敵対的レビュー

本文と図の両方を対象に `adversarial-review` を実行します。REFUTED を直したら、直した箇所をもう一度確かめます。PASS になるまで工程 10 に進みません。

## 10. 公開

レビューが通ったあとで、次の順に進めます。

1. `isPublished: true` にする
2. 関連する既存の記事から、この記事へリンクを 1 本張る（公開記事から下書きへのリンクは検査で落ちるので、ここで張ります）
3. 新しい外部 URL を単独行に置いたなら `pnpm link-cards:warm` を実行する
4. `pnpm lint` と `pnpm build` を実行する
5. コミットして PR を作り、auto-merge を有効にする。筆者が PR まで依頼していないときは、push の前に確認を取る
6. 実行した工程と結果を完成レポートにまとめ、`writing` の Phase 7 の項目とあわせて報告する

## 省略してよい理由にならないもの

| 出てくる考え                                                  | 実際                                                                                       |
| :------------------------------------------------------------ | :----------------------------------------------------------------------------------------- |
| 素材はそろっているので grill は要らない                       | grill が集めるのは素材に無い事実です                                                       |
| ファクトチェックと重複するので `verify-doc-claims` は回さない | 工程 6 がそのファクトチェックです。別の形に置き換えません                                  |
| 短い記事なので反証は 1 点に絞る                               | 敵対的レビューは `adversarial-review` の手順で行います。主張が少なければ行も少なくなります |
| スクリーンショットがあるので図は要らない                      | 図が要らないなら、工程 2 で理由を書いて承認を取ります                                      |
| 急ぎなので後で直す                                            | 公開した情報は、画像の配信元や履歴に残ります。公開前に通します                             |

工程を減らせるのは、筆者がその工程を名指しして省くと言ったときだけです。「急いで」は省く指示ではありません。
